# Go Chi Boilerplate

A deliberately small production baseline for HTTP APIs built with Go, Chi,
PostgreSQL, pgx, and sqlc.

The repository is a starting point, not an application framework. It provides
boring infrastructure defaults and one example vertical module. Authentication,
caching, queues, email, and vendor integrations are intentionally excluded.

## Stack

- Go 1.26.6+
- Chi and the standard `net/http` stack
- PostgreSQL through `pgx/v5`
- Type-safe SQL generated by `sqlc`
- Versioned SQL migrations with Goose
- OpenAPI as the public HTTP contract
- Generated OpenAPI request and response types
- Strict JSON decoding and transport validation
- Configurable fail-closed CORS and trusted client IP handling
- Structured JSON logs with `log/slog`

## Create a project from this template

1. Copy or use this repository as a template.
2. Replace the placeholder module path everywhere:

   ```sh
   go mod edit -module github.com/your-org/your-project
   rg -l 'github.com/lukuku-dev/go-chi-bp' --glob '*.go' --glob '.golangci.yml' | \
     xargs sed -i.bak 's#github.com/lukuku-dev/go-chi-bp#github.com/your-org/your-project#g'
   find . -name '*.bak' -delete
   gofmt -w .

   # Only this README should still mention the placeholder path.
   rg 'github.com/lukuku-dev/go-chi-bp' --glob '!README.md'
   ```

   `.golangci.yml` must be included. Its depguard rules name the module path
   literally, and a rule that no longer matches any import is not an error:
   lint keeps reporting zero issues while the architecture boundaries it is
   supposed to enforce are silently gone.

3. Rename the `widget` example module to the first real business capability,
   including its sqlc output path and depguard file rules.
4. Update `api/openapi.yaml`, migrations, queries, and generated code together.
5. Run `make check` before the first commit.

## Quick start

Requirements: Go 1.26.6+, Docker, and Docker Compose.

```sh
cp .env.example .env
make tools
make hooks
make db-up
make migrate-up
make run
```

The API listens on `http://localhost:8080` by default.

```sh
curl http://localhost:8080/health/live
curl http://localhost:8080/health/ready
curl -X POST http://localhost:8080/v1/widgets \
  -H 'Content-Type: application/json' \
  -d '{"name":"first widget"}'
```

## Browser API defaults

JSON request bodies must use `Content-Type: application/json`, stay within
`HTTP_MAX_REQUEST_BYTES`, contain one JSON value, use known fields, and pass
transport validation. OpenAPI-generated boundary types keep DTOs aligned with
the contract.

CORS is enabled only when `HTTP_CORS_ALLOWED_ORIGINS` contains a comma-separated
allowlist. Credentialed wildcard CORS is rejected at startup. Client addresses
default to the direct TCP peer. Deployments behind a trusted proxy must select
one explicit `HTTP_CLIENT_IP_MODE`:

- `header` for a proxy-overwritten single-IP header;
- `xff-cidrs` for trusted proxy CIDR ranges;
- `xff-count` for an exact, fixed number of trusted proxy hops.

Never select a forwarded-header mode unless the edge strips or overwrites
client-supplied forwarding headers.

## Shutdown

On `SIGINT` or `SIGTERM` the application fails its readiness probe, keeps
serving for `SHUTDOWN_DRAIN_DELAY`, and only then drains in-flight requests
within `SHUTDOWN_TIMEOUT`. The delay exists because readiness is polled on an
interval: a router keeps sending traffic for up to one poll after the probe
starts failing, and shutting down at once would drop exactly those requests.

Set the delay above the readiness poll interval of whatever routes traffic.
`.env.example` sets `0s` because local development has no such router, and
waiting would only slow `make run` down.

The modular monolith is the production default. The microservice guide describes
how to extract a proven capability without introducing distributed infrastructure
or shared data ownership prematurely.

The `internal/app` composition harness can assemble the API with production
adapters or test doubles. Capability cores remain independent of Chi, pgx, and
generated code; concrete HTTP and PostgreSQL adapters live in capability-owned
child packages so future extraction changes adapters rather than business rules.
